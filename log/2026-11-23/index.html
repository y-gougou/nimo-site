    2026-11-23 · AI 工具链实战：Antigravity 风控、客户端更新与防封环境排错¶

    📅 学习日志 · 2026 年 11 月 23 日 · 给防封环境叠加第二套 AI 工具（Google Antigravity）撞上「买号隐藏雷」；同日把 Clash Party 升到 2.0.5 并完整修复更新引入的 DNS/覆写回退；复盘「客户端意外关闭」发现是关机崩溃的良性误报——全程 11 项环境自检保持健康。

    一句话总结

    Antigravity 教会了我「服务级封禁」与「账号封禁」的区别（Google 号一切正常，但 AI 服务被 403 永久关闭）；Clash Party 2.0.5 的「DNS 覆写守卫」和覆写脚本开关被更新重置，导致分流规则一度回退成订阅原版——通过源码级定位 + 一键修复脚本把环境恢复到更新前状态，并把「更新后修复」沉淀成可复用工具。

    第一部分 · Antigravity 的三道地区校验¶

    Google Antigravity 对「非支持地区」的风控比想象中更严，而且不是看单一信号：

    校验一：账号关联的国家/地区（Google 账号资料里的归属地）
校验二：当前出口 IP 的地区
校验三：该地区是否在官方开放名单内
三者有一个不符 → not eligible / Region Restricted

    所以「地区是美国 + IP 是美国」还不够——账号资料里的归属地也必须对得上。这解释了为什么买来的号经常死在资格校验上。

    桌面客户端不走系统代理的坑

    多篇教程提到桌面客户端「不走系统代理」导致登录超时。在我们的环境里这个问题天然免疫：TUN 虚拟网卡全局接管，任何程序的流量都被强制送进分流规则。

    第二部分 · 服务级封禁：Google 号正常但 Antigravity 直接 403¶

    用买来的 Google 号登录 Antigravity：登录成功、订阅显示正常，但一发消息就收到：

    This service has been disabled in this account for violation of Terms of Service.
Please submit an appeal to continue using this product.
(HTTP 403 PermissionDenied)

    这是「服务级封禁」——封的不是 Google 账号，而是这个账号使用 Antigravity 的资格。类比理解：

    账号封禁  = 整张银行卡被冻结（所有服务全断）
服务封禁  = 只有某个会员权益被取消（账号其他功能正常）

    为什么买到这种号：带 AI 订阅的成品号很多是批量生产、被前手拿去做自动化滥用的，Google 的服务级封禁（年初那波大规模封号潮）早就把这类号的 AI 服务资格剥夺了。买号时「地区对、订阅在」都不等于「资格还在」——必须实际跑一次才知道。

    申诉要点（官方论坛的规则）：

    • 表单只能提交一次，重复提交不会加速、可能延长
    • 自动审核 48-72 小时，不发确认邮件，通过后下次登录自动恢复
    • 一次性政策：恢复后再违规 = 永久封禁
    • 内容如实简短，不要编造"人在美国"之类的细节

    第三部分 · Clash Party 2.0.5 更新：DNS 覆写守卫与覆写回退¶

    从 2.0.1 升到 2.0.5 后，环境出现两处回退，都值得记下来：

    3.1 DNS 覆写守卫（DnsOverrideGuard）¶

    2.0.3 新增的「订阅 DNS 覆写保护」机制，源码逻辑是：

    检测订阅配置里是否有自定义 DNS 字段
（proxy-server-nameserver / nameserver-policy 等）
   ↓ 有
在用户未显式确认前，自动禁用应用级 DNS 覆写
   ↓
并把 controlDns 持久化成 false

    我们的订阅恰好自带自定义 DNS（引用了订阅里的节点组），于是守卫把我们的应用级 DNS（fake-ip + 海外解析 + 国内直连策略）整个关掉了。修复：

    # config.yaml
controlDns: true                 # 重新启用应用 DNS 覆写
disableDnsOverrideGuard: true    # 关掉守卫, 不再自动禁用
useNameserverPolicy: true        # 启用策略
nameserverPolicy:
  geosite:cn:
    - "https://223.5.5.5/dns-query"
    - "https://119.29.29.29/dns-query"

    3.2 覆写脚本被重置¶

    更新把全局 JS 覆写条目（负责白名单分流 + 焊死兜底的那 24 条规则）的 global 标志改成了 false——规则整体回退成订阅原版（14 个分组、354 条规则、兜底还带 DIRECT 回落）。发现方式：

    核心日志出现订阅原版分组名（"📢 使用提示｜…"）
→ work/config.yaml 分组不是「海外出口」
→ 规则数 354 而不是 24
→ 覆写条目 global: false

    把 global: true 改回来后一切恢复。教训：客户端大版本更新后，必须做一次全量验收，而不是只看"能不能上网"。

    第四部分 · 「意外关闭」真相：关机崩溃的良性误报¶

    晚上发现 Clash Party「意外关闭」，第一反应是泄漏。用证据链还原：

    1. journalctl --list-boots → 找到昨晚 23:22 是一次正常 systemctl reboot
2. /var/crash 里的崩溃转储 → mihomo-party 的 Signal 是 SIGTRAP
3. 日志时间线 → 崩溃发生在「关机退出流程」中, 不是运行时
4. 今天开机后 GUI/核心从 17:11 连续运行, 无退出记录

    结论：崩溃发生在关机退出的瞬间（Electron 应用被 SIGTERM 时常见的良性崩溃），不是运行中闪退。泄漏分析：

    关机瞬间 → 整个网络栈随系统一起关闭 → 不存在"系统在跑、代理已死、还能发包"的窗口
运行期间 → 防火墙是内核规则, 独立于客户端, 客户端死 = 断网
开机后   → 防火墙 7 秒内生效, 且此时浏览器还没启动

    「感觉被捕捉到了泄漏」= 关机崩溃带来的惊吓，不是真实的泄漏事件。

    第五部分 · 今日沉淀¶

    5.1 更新后修复脚本¶

    把今天的修复过程沉淀成幂等脚本，以后每次更新客户端后跑一次：

    # 先退出 Clash Party, 然后:
bash ~/.local/bin/clash-party-postupdate-fix.sh
# 重新打开客户端后验证:
bash ~/.local/bin/clash-guard-check.sh   # 期望 11/11 全过

    5.2 版本回退预案¶

    • 旧版本安装包提前下载到本地（dpkg -i 直接回退）
    • 更新前的完整配置备份（含一键还原脚本）

    5.3 多账号隔离策略验证¶

    Antigravity 的雷炸在「消耗号」上，绑定 Claude 的主力 Google 号全程无伤——这正是之前分账号决策的价值：每个 AI 服务用独立账号，服务级封禁不会连坐。

    今日总结¶

    1. 「能登录」不等于「有资格」：买号要实测每个服务的资格，地区/订阅只是表象
    2. 客户端更新 = 重新验收：覆写开关、DNS 覆写、规则兜底都可能被静默重置，11 项自检脚本要跑一遍
    3. 证据链胜过直觉：面对"感觉泄漏了"的恐慌，用启动历史 + 崩溃转储 + 日志时间线还原事实，而不是凭感觉下结论
    4. 经验要沉淀成工具：修复脚本 + 回退安装包 + 配置备份，让下次更新从"踩坑"变成"跑脚本"

    环境整体保持 11/11 健康：白名单分流、断网防火墙、指纹浏览器、账号隔离全部在位。
