    2026-08-22 · Docker 全链路实战与概念补强¶

    📅 学习日志 · 2026 年 8 月 22 日 · Docker 补强：Windows 实战 + 概念进阶 + ROS/GPU 规划

    一句话总结

    在 Windows 上完成 Docker Desktop 从“已安装但 Engine 起不来”到可用的全过程：安装并启用 WSL 2、配置 Docker Hub 镜像源、允许内网 HTTP Registry、从 Ubuntu Registry 拉取 nginx 镜像、映射 8080 端口运行，并用状态、日志、端口和 HTTP 响应完成一次证据驱动的排错。

    📌 今日学习清单¶

    # 今日收获 一句话
    1 Docker Desktop 的角色 不只是 GUI，而是 Windows 上的 Linux 容器运行环境和集成层
    2 Windows Docker 架构 PowerShell → Docker CLI → Docker Desktop → WSL 2 → Docker Engine
    3 WSL 2 前置条件 Docker Desktop 进程存在，不代表 Engine 已经启动
    4 镜像源配置 registry-mirrors 主要用于 Docker Hub 拉取加速
    5 HTTP Registry insecure-registries 是允许明文 HTTP，不是证书信任
    6 Registry 连通性 /v2/ 返回 200 {}，说明已连到 Registry API
    7 镜像拉取 成功拉取 172.20.10.4:5000/nginx-demo:v1
    8 端口映射 Windows 8080 → 容器 nginx 80
    9 排错证据链 Desktop 状态 → 镜像 → 容器 → 日志 → 端口 → HTTP
    10 命名也会制造假故障 web-server 实际写成 web-derver，导致按错误名字查询失败

    第一部分 · Docker Desktop 已打开，为什么 Docker 还不能用¶

    安装 Docker Desktop 后，托盘和后台进程都存在，但执行：

    docker version

    只能看到 Client，Server 返回：

    Docker Desktop is unable to start

    这说明：

    Docker CLI 已安装
≠ Docker Engine 已启动

    继续读取 Docker Desktop 错误日志，找到真正原因：

    engine linux/wsl failed to start
checking WSL version
wsl is not installed

    根因不是镜像源、不是 Docker 配置格式，而是 Linux 容器运行所需的 WSL 环境不存在。

    今天最重要的排错动作

    不根据“鲸鱼图标出现了”猜 Docker 正常，而是用 docker version 区分 Client 和 Server，再用日志定位 Engine 的启动前置条件。

    第二部分 · 安装 WSL 2，让 Linux Engine 真正启动¶

    安装 WSL 组件，并把默认版本设置为 2：

    wsl.exe --install --no-distribution
wsl.exe --set-default-version 2

    这里使用 --no-distribution，因为 Docker Desktop 不要求额外安装一个 Ubuntu 用户发行版；它可以管理自己的 Linux 运行环境。

    随后启动 Docker Desktop，再次验证：

    docker desktop status
docker version

    结果同时出现 Client 和 Server：

    Docker Desktop 4.87.0
Docker Engine 29.7.2
Linux/amd64

    至此链路变成：

    flowchart LR
    A[PowerShell] --> B[Docker CLI]
    B --> C[Docker Desktop]
    C --> D[WSL 2 Linux 内核]
    D --> E[Docker Engine]
    E --> F[Linux 容器]

    第三部分 · 配置 Docker Hub 镜像源¶

    在 Docker Desktop 的 Settings → Docker Engine 中保留原配置并加入：

    "registry-mirrors": [
  "https://docker.m.daocloud.io",
  "https://mirror.ccs.tencentyun.com",
  "https://docker.1ms.run"
]

    没有一次塞入十几个来源，原因是失效镜像可能增加等待时间；同时删除了 HTTP 公共镜像，避免不必要的明文传输。

    重启后验证实际生效值，而不是只看配置文件：

    docker info

    Engine 返回了三个 Registry Mirrors，随后成功拉取并运行 hello-world：

    docker pull hello-world
docker run --rm hello-world

    看到：

    Hello from Docker!

    第四部分 · 允许内网 HTTP Registry¶

    Ubuntu 机器上的 Registry 地址：

    172.20.10.4:5000

    它使用 HTTP，而 Docker 默认按 HTTPS 访问，所以在 Docker Engine JSON 中加入：

    "insecure-registries": [
  "172.20.10.4:5000"
]

    完整核心配置：

    {
  "builder": {
    "gc": {
      "defaultKeepStorage": "20GB",
      "enabled": true
    }
  },
  "experimental": false,
  "features": {
    "buildkit": true
  },
  "registry-mirrors": [
    "https://docker.m.daocloud.io",
    "https://mirror.ccs.tencentyun.com",
    "https://docker.1ms.run"
  ],
  "insecure-registries": [
    "172.20.10.4:5000"
  ]
}

    验证 Docker 已按 HTTP 仓库识别：

    docker info

    结果中该 Registry 显示：

    Secure: false

    再直接检查 Registry V2 API：

    curl.exe http://172.20.10.4:5000/v2/

    返回：

    HTTP 200
{}

    insecure 的准确含义

    这不是把仓库证书加入信任链，而是明确允许未加密的 HTTP。它适合可信实验内网，不适合跨互联网或正式生产环境。

    第五部分 · 拉取并运行 nginx-demo¶

    拉取：

    docker pull 172.20.10.4:5000/nginx-demo:v1

    镜像全名拆解：

    172.20.10.4:5000   Registry 地址
nginx-demo         镜像仓库名
v1                 版本标签

    运行：

    docker run -d `
  -p 8080:80 `
  --name web-server `
  172.20.10.4:5000/nginx-demo:v1

    请求路径：

    Windows 浏览器
→ http://127.0.0.1:8080
→ Windows 8080
→ Docker Desktop 端口转发
→ 容器 80
→ nginx

    第六部分 · “网页打不开”的真实排查¶

    最初按预期名称检查：

    docker inspect web-server

    返回：

    No such object: web-server

    这看起来像容器根本没启动。但不能停在这一步，继续查看所有容器：

    docker ps -a

    发现真正运行的是：

    NAME         IMAGE                                      STATUS
web-derver   172.20.10.4:5000/nginx-demo:v1             Up

    原来只是把 server 写成了 derver。

    继续验证状态、日志和端口：

    docker inspect web-derver
docker logs web-derver
docker port web-derver
curl.exe -v http://127.0.0.1:8080/

    证据：

    • 容器状态 running
    • nginx 日志显示配置完成并启动 worker
    • 端口为 0.0.0.0:8080->80/tcp
    • curl 成功建立到 127.0.0.1:8080 的连接
    • nginx 返回 HTTP/1.1 200 OK
    • 页面内容是 Welcome to nginx!

    所以 Docker、端口转发和 nginx 都正常。若浏览器仍失败，应检查浏览器是否自动使用了：

    https://127.0.0.1:8080/

    正确地址是：

    http://127.0.0.1:8080/

    容器名称可修正：

    docker rename web-derver web-server

    第七部分 · Docker Desktop 到底相当于什么¶

    今天最后补上的核心认知：

    Linux：
Linux 内核 → Docker Engine → 容器

Windows：
Windows → Docker Desktop → WSL 2 Linux 内核 → Docker Engine → Linux 容器

    Docker Desktop 不只是一个“桌面版 docker”，它把 Windows 上缺失的 Linux 运行环境、Engine、网络、文件共享、Compose 和 GUI 管理都组合在了一起。

    PowerShell 里的 docker 只是客户端；真正的 nginx 进程运行在 WSL 2 Linux 内核之上的容器中。

    今日最终验证结果¶

    Docker Desktop       running
WSL 默认版本          2
Docker Engine        正常响应
Registry Mirrors     3 个 HTTPS 镜像源
HTTP Registry        172.20.10.4:5000，连通且已允许
nginx-demo:v1        拉取成功
nginx 容器            running
Windows 8080         已映射到容器 80
HTTP 请求             200 OK

    今日方法论¶

    今天最重要的不是记住更多命令，而是形成分层排查顺序：

    Docker Desktop / WSL
        ↓
Docker Engine
        ↓
Registry 与镜像
        ↓
容器状态与日志
        ↓
端口监听
        ↓
HTTP 响应与浏览器

    每一层都先拿证据，再进入下一层。这样“网页打不开”不会被笼统地归结为 Docker 坏了。

    第一部分 · 解剖镜像：docker history / docker inspect¶

    docker history <镜像> —— 看镜像的"族谱"（每一层是谁建的、多大）：

    docker history ypproject:v1

IMAGE      CREATED BY                                    SIZE
6c63a5535e75  CMD ["python" "main.py"]                   0B      ← CMD 不占空间
<missing>  pip install -r requirements.txt              9.7MB   ← RUN 有重量
<missing>  COPY dir:...                                 24.6kB  ← COPY 搬代码
<missing>  WORKDIR /app                                 8.19kB
<missing>  RUN ... (装 Python)                           41.4MB  ← 基础镜像的层
<missing>  ENV PYTHON_VERSION=3.12.14                    0B      ← ENV 是层但 0B
<missing>  debian 系统层                                 87.4MB  ← 最胖
    • 从上往下 = 从新到旧；<missing> = 中间层（正常）
    • ENV 等只改元数据的指令 SIZE 是 0B —— 不产生文件系统层

    docker inspect <镜像> —— 看镜像的完整 JSON 配置：

    docker inspect nginx --format '{{.Config.Env}}'
docker inspect nginx --format '{{.Config.ExposedPorts}}'
    • RepoTags：多个 tag 指向同一镜像（名片效果实锤）
    • ExposedPorts：镜像声明想开的端口
    • Entrypoint / Cmd：容器启动时实际执行的入口命令

    第二部分 · ENV / EXPOSE / ENTRYPOINT¶

    ENV —— 设置环境变量：

    ENV APP_NAME=ypapp
ENV APP_PORT=8080
CMD ["bash", "-c", "echo $APP_NAME is running on port $APP_PORT"]
→ 运行输出：ypapp is running on port 8080

    EXPOSE —— 声明想开的端口（只是声明！）：

    EXPOSE 8080
→ inspect 里 ExposedPorts 有 8080/tcp
→ 但 docker ps 的 PORTS 列是空的！
→ 真正对外开门还是要 -p（声明 ≠ 开门）

    CMD vs ENTRYPOINT（对比实验结论）：

    docker run cmd-demo                      → hello from CMD
docker run cmd-demo echo "我传的参数"      → 我传的参数（★ CMD 整组被替换）
docker run entry-demo                    → hello from ENTRYPOINT
docker run entry-demo "我传的参数"         → hello from ENTRYPOINT 我传的参数（★ 参数追加）

CMD        = 默认值，可被 docker run 后面内容"整组替换"
ENTRYPOINT = 固定程序，docker run 后面内容"追加"到它后面

    踩的坑：CMD 里引号没配对 → Unterminated quoted string；变量名忘写 $ → 输出原文字。CMD 的 JSON 数组形式引号容易错，写简单点。

    科研经典用法：

    ENTRYPOINT ["python"]        固定执行 python
CMD ["main.py"]              默认参数 main.py
docker run myimg                  → python main.py
docker run myimg train.py         → python train.py

    第三部分 · 两电脑模拟云服务器部署（实操）¶

    链路（电脑 A = Ubuntu 开发机，电脑 B = Windows 当"服务器"）：

    电脑 A（Ubuntu）:
  docker tag nginx 172.20.10.4:5000/nginx-demo:v1   # 贴地址名片
  docker push 172.20.10.4:5000/nginx-demo:v1        # 上传到本地仓库
电脑 B（Windows）:
  docker pull 172.20.10.4:5000/nginx-demo:v1        # 从仓库取货
  docker run -d -p 8080:80 --name web-server ...    # 跑起来对外开门
电脑 A 验证:
  curl http://172.20.10.12:8080 → HTTP 200 ✅

    网络前提： - 两台电脑同一局域网（手机热点 172.20.10.x 也行） - ping 不通 ≠ 不能通信（Windows 防火墙拦 ICMP 是正常的，要用 TCP 验证） - 手机热点一般没开 AP 隔离，可互访

    关键坑：insecure-registries： - 本地仓库是 HTTP 非 HTTPS，Docker 默认拒绝（localhost 例外） - Ubuntu 和 Windows 都要配白名单： - Ubuntu：/etc/docker/daemon.json → "insecure-registries": ["172.20.10.4:5000"] + 重启 docker - Windows：Docker Desktop → Settings → Docker Engine → 同样配置 + Apply & Restart - 报错特征：http: server gave HTTP response to HTTPS client

    镜像名格式复盘：

    172.20.10.4:5000/nginx-demo:v1
└──┬───┘└─┬─┘└──┬───┘└┬┘
电脑地址  端口  镜像名  版本
= 去 172.20.10.4 的 5000 号门（仓库）取 nginx-demo 的 v1 版本

    docker run -d -p 8080:80 --name web-server 参数： - -d：后台运行（不占终端） - -p 8080:80：端口映射（左边=这台电脑的门，右边=容器内的门） - --name：给容器起名（操作不用记随机 ID）

    HTTP 200 = 服务器回复"一切正常，你要的东西给你了"（类比：快递签收成功）

    第四部分 · 云服务器 Docker 补充¶

    真实部署和两电脑模拟的对应：

    模拟时                    真实云服务器
Ubuntu 的 registry    →   Docker Hub / 私有仓库
Windows（当服务器）    →   云厂商的一台机器
局域网                 →   公网
172.20.10.4:5000      →   你的 Docker Hub 账号名

    服务器场景关键命令：

    ssh 用户名@服务器公网IP                    # SSH 远程登录
docker run -d --restart=always -p 8080:80 镜像   # --restart=always 自动重启
docker logs -f <容器>                      # 看日志（-f 跟随）
docker run -d -v /data:/app/data 镜像      # 数据挂载（数据留在服务器）
docker login                              # Docker Hub 登录认证

    --restart 级别：no（默认）/ on-failure（异常退出时重启）/ always（任何时候，服务器推荐）

    安全：不给不可信账号加 docker 组（=root 权限）；密钥登录；防火墙只开必要端口。

    第五部分 · ROS Docker 深入（结合毕设）¶

    核心痛点：ROS1 Melodic 只能装 Ubuntu 18.04，而当前系统是 26.04 —— 直接装不了。

    ROS1 Melodic → Ubuntu 18.04
ROS1 Noetic  → Ubuntu 20.04
ROS2 Humble  → Ubuntu 22.04
ROS2 Jazzy   → Ubuntu 24.04

    解法：docker pull ros:melodic —— 现成的 18.04 + Melodic 环境，主机不受影响。

    ROS 容器启动命令（逐参数拆解）：

    docker run -it \
  --name wheeltec-ros \
  --device=/dev/ttyUSB0 \      # 把串口设备借给容器（新知识！）
  --device=/dev/ttyUSB1 \      # 底盘串口 + 电流模块串口
  -p 9090:9090 \               # rosbridge WebSocket
  -p 8000:8000 \               # web_dashboard HTTP
  -v ~/ros_ws:/workspace \     # 代码挂载
  ros:melodic

    --device：容器默认看不见硬件（摄像头/串口/GPU 都隔离），--device=/dev/ttyUSB0 = 把宿主机设备"借给"容器（和 -v 挂目录同理，挂的是硬件）。

    ROS1 特殊点： - 需要 roscore（master）先启动，节点才能互相发现 - 单机系统（一个 master + 多个节点 + 串口）最自然是一个容器装全部

    Jetson 小车（毕设平台）： - ARM 架构 + NVIDIA 定制 JetPack，版本绑定：JetPack 4.x=18.04 / 5.x=20.04 / 6.x=22.04 - 不能随便刷系统：刷了新 JetPack 就装不了 Melodic；且 ros:melodic 官方镜像是 x86，Jetson(ARM) 拉不下来 - 结论：Jetson 保持现状（部署端），Docker 的价值在本地开发机（x86）

    开发方案：本地 26.04 + Docker ros:melodic（x86 镜像）+ 最新 VSCode/AI 助手 → git push → SSH 连 Jetson → git pull 部署。Python 代码跨架构，本地 x86 容器开发可直接在 ARM Jetson 跑。

    rosbag（话题录制回放）—— 解决"没硬件测不了"：

    rosbag record -a        # 在小车录所有话题数据 → .bag 文件
rosbag play xxx.bag     # 本地回放话题数据（算法节点以为真车在线）
    • 录一次真实数据，本地无限次回放调试，不用每次上车
    • ROS 节点分两类：🔴 读串口的驱动节点（必须真车，约 2 个）vs 🟢 处理话题的算法节点（本地就能跑，占 80%）

    第六部分 · GPU/CUDA Docker（概念）¶

    为什么特殊：容器默认看不见 GPU（和串口一样被隔离），直接跑深度学习镜像只会用 CPU。

    解法：宿主机装 NVIDIA Container Toolkit → docker run --gpus all

    docker run --gpus all nvidia/cuda:12.0-runtime nvidia-smi   # 容器里能看到 GPU

    核心分层（记牢）：

    NVIDIA Driver（驱动）       → 必须在宿主机（内核层面，容器不共享）
NVIDIA Container Toolkit    → 宿主机装一次
CUDA / PyTorch 环境          → 放容器（镜像里装，随取随用）

    常用镜像：

    nvidia/cuda:12.x-base          纯 CUDA（最小）
pytorch/pytorch:2.x-cuda12     PyTorch 官方（科研最常用）
tensorflow/tensorflow:2.x-gpu  TF 官方 GPU 版

    和 ROS 呼应：串口 --device=/dev/ttyUSB0，GPU --gpus all —— 同一个思路：容器默认隔离硬件，需要时"借"进来。

    今日总结¶

    今天把 Docker 提纲内的欠账清零了（history/inspect + ENV/EXPOSE/ENTRYPOINT），云服务器部署从概念升级为两电脑实操，ROS/GPU 从"将来的事"变成了结合毕设的清晰路线。Docker 主干至此完整收官。

    核心认知升级： 1. 镜像分层不是抽象概念，history 能看到每一层的指令和大小 2. CMD 整组替换 vs ENTRYPOINT 参数追加 —— 用对比实验刻进脑子 3. 云部署流程已亲手走通（两电脑模拟），真实服务器只是换地址 4. ROS Docker 的痛点 = 版本锁定（Melodic 只认 18.04），解法 = 本地容器开发 + rosbag 回放 5. Jetson 刷系统要谨慎（JetPack 绑定），它适合当"部署端"而不是"开发端" 6. GPU 容器 = Driver 在宿主 + CUDA 在容器 + --gpus all
