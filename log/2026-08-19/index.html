    2026-08-19 · Docker 基础主干与工程入门¶

    📅 学习日志 · 2026 年 8 月 19 日 · 自动化专业 / 容器技术

    一句话总结

    Docker 主干一日通关：容器生命周期、数据持久化、端口映射、容器网络、Dockerfile、Compose、Registry 全流程走完，并补上前端/后端与网络寻址的基础概念。挫折很多（今天踩了 15 个坑），但每个坑都是教材 —— 文末有完整的坑与教训清单。

    第一部分 · 容器生命周期¶

    昨天学会了 docker run（创建 + 进入 + 退出）。今天学不重新创建，直接操控已有容器 —— 核心是生命周期状态机：

    create → start → running → stop → exited → rm
          ↑                          ↓
          └────── start（再启动）──────┘

    实验观察：

    • docker start <容器>：容器 ID 不变，STATUS 从 Exited → Up —— start 是唤醒，不是新建
    • docker exec -it <容器> bash：钻进运行中的容器，exit 退出后容器继续跑（PID 1 还活着）—— 与 run -it 里 exit 杀掉 PID 1 完全不同
    • 容器里敲 docker 报 command not found：CLI 是宿主机工具，容器里没有 —— 隔离的铁证
    • docker stop：docker ps 里消失、ps -a 里变 Exited —— 停车 ≠ 删除
    • docker rm：从 ps -a 彻底消失 —— 报废，不可恢复；但镜像还在（模具还在）

    意外收获 —— 退出码：hello-world 是 Exited (0)（正常结束），而 stop 的 bash 容器是 Exited (137)（128+9，被 SIGKILL 强杀）。docker stop 会先发温柔信号等 10 秒，不响应才强杀。

    第二部分 · 容器数据（Bind Mount + Volume）¶

    问题：容器是临时的，rm 一删，里面写的东西全跟着消失。镜像只会重建"干净的初始环境"。

    解法一：Bind Mount（自己管宿主机目录）

    docker run -v ~/docker-data:/data ubuntu bash
    • 挂载 = 同一个地方的两个视角，不是复制；写入双向可见
    • 容器删了，宿主机目录毫发无损（类比：给容器插 U 盘）
    • 适用：代码、配置文件、ROS workspace（你想亲眼看到文件）

    只读挂载（保护原始数据）：有些数据你不希望容器修改 —— 比如原始数据集、配置模板。加 :ro（read-only）后容器只能读、不能改宿主机文件：

    docker run -v ~/dataset:/data:ro ubuntu bash

    或更明确的写法：

    docker run --mount type=bind,source=$HOME/dataset,target=/data,readonly ubuntu bash

    对科研原始数据尤其好用 —— 万一容器里程序写错，宿主机上的数据集分毫不动。

    解法二：Volume（Docker 管数据目录）

    docker volume create mydata
docker run -v mydata:/data ubuntu bash
    • 卷名（无 / 开头）= Volume；路径（/ 或 ~ 开头）= Bind Mount，系统靠这个区分
    • 数据跟卷走，不跟容器走 —— 跨容器共享、抗容器删除
    • 卷被容器引用时删不掉（volume is in use）—— 先删容器才能删卷
    • 适用：数据库数据、程序生成的数据（不想手动碰文件）

    ⚠️ 重点：Volume ≠ 永久备份 —— 卷活在你宿主机磁盘上；宿主机/云服务器没了，卷也没了。真正的保险 = 定期备份到外部存储（对象存储/NAS/异地）。

    第三部分 · 端口映射（对外开门）¶

    docker run -d -p 8080:80 --name web-demo nginx
    • -d = 后台运行；--name = 起名字；-p 外面:里面 = 端口映射
    • 为什么两个端口：容器有独立的网络世界，房间里的 nginx 监听"房间内"的 80，外面够不到。-p = 在墙上开窗，Docker 转接
    • 验证：curl http://127.0.0.1:8080 返回 nginx 欢迎页 HTML；docker ps 的 PORTS 列 0.0.0.0:8080->80/tcp 是施工图
    • 端口默认值只是习惯，不是法律（Jupyter 8888、数据库 5432、ROSBridge 9090 都可改）

    安全补充：-p 8080:80 通常绑定所有网络接口；只需本机访问时，更稳妥的写法是 -p 127.0.0.1:8080:80。

    第四部分 · 容器网络（对内组网）¶

    docker network create ypnet
docker run -d --name web1 --network ypnet nginx
docker run --rm --network ypnet busybox wget -O- http://web1   ← 用名字访问！
    • 三种模式：bridge（默认）/ host / none
    • 核心：同一自定义网络里的容器，用名字互访（Docker 内置 DNS）
    • 防混关键：-p = 对外开门（外面→容器）；--network = 内部专线（容器↔容器）
    • 未来架构：前端容器 →(名字)→ 后端容器 →(名字)→ 数据库容器；对外只开前端一扇门

    第五部分 · 补课：前后端与网络基础¶

    这是为了补 Docker 网络的地基 —— 来自真实 Web 世界的通用知识。

    • 前端 = 用户看到、操作的部分（浏览器页面）；后端 = 干活的程序（处理请求、操作数据）。两者是两个独立程序，靠"请求-响应"通信
    • 寻址两层：IP = 哪台电脑（楼），端口 = 哪个程序（房），IP:端口 定位一个服务 —— 学校 API 的 baseURL xplt.sdu.edu.cn:4000 就是这个格式
    • 完整请求链路：浏览器 → 解析域名成 IP → 连接 IP:端口 → 发请求 → 后端处理 → 响应回来
    • 回看 dsh：浏览器 → 127.0.0.1:3080（端口寻址）→ dsh 后端 → 学校 API（前端访问后端的完整实例）

    第六部分 · Dockerfile（环境的源代码）¶

    FROM python:3.12-slim    # 地基（基础镜像）
WORKDIR /app             # 工作目录
COPY . .                 # 把代码搬进镜像（第一个. = 构建上下文，第二个. = 镜像里的 /app）
RUN pip install -r requirements.txt   # 构建时执行（盖房时砌墙，只一次）
CMD ["python","main.py"] # 启动时执行（住进去开灯，每次启动都执行）
    • 流程：Dockerfile → docker build -t 名字:版本 . → 镜像 → docker run → 容器
    • 镜像分层：Dockerfile 按 instruction 顺序构建，修改文件系统的构建指令会形成镜像层，Docker 利用这些层做缓存和复用（LABEL 这类只改 metadata 的指令不产生新的文件系统层）
    • RUN vs CMD：RUN = 造镜像时做一次；CMD = 每次启动容器都做
    • .dockerignore：Docker 的黑名单，排除缓存/数据集/密钥进镜像（COPY . . 不挑食！）

    可复现 ≠ 永远完全一样：FROM python:3.12-slim 这类 tag 是可变的 —— 几个月后再 build，同一个 tag 可能已指向更新后的基础镜像。严格要求复现时，应固定更具体的版本（甚至 digest）。科研工作流的复现强度排序：

    Dockerfile + 明确软件版本 + requirements/lock 文件 + 镜像 tag/digest → 最强复现

    另外：API Key、密码、SSH Key 不要用 ARG/ENV 烧进镜像（可能残留在最终镜像或元数据里）—— Docker 官方建议敏感信息用 build secrets。

    第七部分 · Docker Compose（多容器编排）¶

    services:                # 环境由哪些服务组成
  web1:
    image: nginx
    ports: ["8080:80"]
  web2:
    image: nginx
    ports: ["8081:80"]

docker compose up -d     # 一键启动全部
docker compose down      # 一键停止+删除容器和网络
docker compose ps        # 看状态
docker compose logs      # 看日志
    • Compose 自动做三件事：建网络（服务名=主机名，互访零配置）、规范命名、一键启停
    • 坑：up 是增量的 —— 失败的残留容器会被复用（端口映射缺失）；诡异状态先 down 清场再 up
    • 数据边界：docker compose down 默认不删除命名 Volume；down -v 才会连卷删除，执行前要确认数据可丢弃

    第八部分 · Registry 与环境迁移¶

    docker tag <已有镜像> <地址/名字:版本>   # 贴"带地址的名片"（不复制，内容不变）
docker push <地址/名字:版本>             # 上传到仓库（地址写在名字里）
docker pull <地址/名字:版本>             # 从仓库下载
docker rmi <镜像名>                      # 删镜像（rm 删容器，rmi 删镜像）
docker login                            # 登录公共仓库（本地仓库不需要）
docker save <镜像> -o 文件.tar           # 离线导出（备份/迁移）
docker load -i 文件.tar                  # 离线导入
    • Registry = 存镜像的仓库：Docker Hub 是公共仓库；当天启动的本地 registry 没配置认证，所以不用登录，但 Registry 是否需要登录取决于服务端配置
    • 镜像名 = 地址 + 名字 + 版本；不带地址 = 默认 Docker Hub（所以 docker run ypproject:v1 会去 Docker Hub 找然后失败）
    • 迁移闭环：build → tag → push → rmi（模拟换机）→ pull → run（环境原样复现）
    • 分层传输：仓库里已有的层不重复传（Layer already exists）
    • 坑：容器占用的镜像删不掉；pull 回来的名字带地址，run 要用全名

    第九部分 · 云服务器部署¶

    # 服务器上（SSH 登录后）：
ssh 用户名@服务器IP                        # 远程进入服务器
sudo apt install -y docker.io docker-compose-v2   # 装 Docker（Ubuntu 仓库路线）
docker pull 你的账号/项目:v1               # 拉镜像（路线 B）
docker run -d --restart=always -p 8080:80 -v ~/data:/data 项目:v1
#                    ↑ 自动重启（服务器 7×24 的生命线）
    • 两条路线：A 代码路线（git clone + build）vs B 镜像路线（pull）—— 科研推荐 B，环境分毫不差
    • 数据挂载在服务器目录；服务器到期前：代码 git push、镜像 docker push、数据备份外部

    安装命令为什么网上有两套（来源区别）：

    Ubuntu 发行版仓库路线：docker.io + docker-compose-v2
Docker 官方仓库路线：   docker-ce + docker-ce-cli + containerd.io
                        + docker-buildx-plugin + docker-compose-plugin

    两套都对，只是来源不同。Docker 官方甚至把 docker.io、docker-compose-v2 等发行版包列为"装官方版前要处理的冲突包"（两者不宜混装）。以后看到网上两套教程就不会懵了。

    资源限制（服务器/科研环境的保命技能）：容器默认不会自动限制能用多少 CPU/内存 —— 一个实验写炸了（内存泄漏/死循环）可能吃掉整台服务器资源。需要时主动限制：

    docker run --memory=8g --cpus=4 my-experiment

    记住一点：容器不是虚拟机那种固定资源盒子，需要时应主动限制 CPU / Memory。这对以后 GPU 云服务器尤其重要。

    第十部分 · 科研 Docker 工作流（方法论）¶

    核心原则：环境、代码、数据 —— 三样东西分开放

    project/                  ← 进 Git（代码 + Dockerfile + compose.yaml + requirements.txt）
├── src/  configs/  Dockerfile  compose.yaml  README.md  .gitignore
/data/                    ← 不进 Git（大文件）
├── datasets/  checkpoints/  logs/  results/

    三套资产的三个流向：

    代码 + Dockerfile → Git（版本化）
镜像 → Registry（环境随取随用）
数据 → 外部存储备份（对象存储 / NAS / 异地）

    运行姿势：docker run -v ~/project:/workspace -v ~/data:/data <镜像> —— 容器一次性，代码和数据从外面挂进来。

    换机器/服务器到期：git clone + docker build/pull + 挂载数据 → run；到期前代码 push、镜像 push、数据备份。

    第十一部分 · Docker 日常排错四件套¶

    服务器上出问题时，这四步的标准排查顺序 —— 比再背十几个 run 参数更有价值。

    docker ps -a             ← 1. 先看容器状态（哪些在跑、哪些挂了、退出码多少）
docker logs <容器>        ← 2. 看程序输出（最直接的问题线索）
docker inspect <容器>     ← 3. 看底层配置（网络/挂载/IP/环境变量）
docker stats             ← 4. 实时看 CPU/内存/网络/磁盘 IO

    四件套详解：

    • docker logs -f <容器> —— 看程序输出，-f = follow 实时跟随（和 journalctl -f 一个思路）
    • docker inspect <容器> —— 查容器对象的完整 JSON 配置（网络、挂载、IP、环境变量等底层信息）
    • docker stats —— 实时监控所有容器的资源占用
    • docker system df —— 看 Docker 到底吃了多少磁盘（按 镜像/容器/卷/构建缓存 分类）

    垃圾清理（Docker 也会产生垃圾）：今天连续 build / run / stop / rm 这么多次，以后会发现 Docker 特别容易积累 stopped 容器、旧镜像、构建缓存。

    docker system df        ← 先查看占用（只读，安全）

docker system prune     ← ⚠️ 清理命令：删除未使用的容器/镜像/网络/缓存
                          弄清楚删除范围后再使用！

    📌 今日坑与教训清单（详细版）¶

    今天踩了 15 个坑，全部记录：报错原文 → 原理 → 解决 → 预防。复习时重点看这里。

    坑 1：docker 组未生效（权限拒绝）¶

    报错：permission denied while trying to connect to the docker API
      at unix:///var/run/docker.sock
场景：昨天执行了 usermod -aG docker 加了组，今天新开的终端还是没权限。
原理：docker 客户端通过 unix socket（/var/run/docker.sock）与引擎通信，
      这个 socket 属于 docker 组。但"组变更"要重新登录才生效 ——
      系统在登录那一刻读取你的组列表，当前会话还是旧身份。
解决：注销重新登录（彻底）；或 newgrp docker 临时切换当前终端。
预防：改完用户组，记得注销重登一次。

⚠️ 安全补充：加入 docker 用户组基本等价于授予 root 级 Docker 控制能力，
不应随意给不可信账号加这个组（云服务器上尤其要注意这一点）。

    坑 2：容器里没有 docker 命令¶

    报错：bash: docker: command not found
场景：在 ubuntu 容器里想敲 docker ps。
原理：容器是隔离的，里面只有镜像自带的东西；docker CLI 是宿主机工具，
      不会出现在容器里。遥控器永远在宿主手里。
解决：在宿主机敲 docker；容器里想用工具先确认镜像里有没有。
预防：记住"容器只有镜像带的东西"。

    坑 3：stop 后退出码 137（被强杀）¶

    现象：docker ps -a 显示 Exited (137)，而 hello-world 是 Exited (0)。
原理：退出码 137 = 128 + 9，9 是 SIGKILL（强杀信号）。
      docker stop 的流程：先发温柔信号（SIGTERM）等 10 秒，
      进程不响应才发强杀。bash 没理会温柔信号 → 被强杀 → 137。
对比：0 = 进程自己正常退出。
预防：看 STATUS 的退出码，能判断容器是"正常下班"还是"被拖走"。

    坑 4：main.py 顶层缩进（Python 语法）¶

    报错：（运行时）IndentationError: unexpected indent
场景：main.py 的 print 前多了 4 个空格。
原理：Python 顶层代码不能缩进 —— 缩进只用于 if/for/def 等代码块内部。
解决：删掉顶层缩进；用 python3 -m py_compile main.py 提前做语法检查。
预防：写 Python 后养成语法检查习惯（编译检查秒出结果）。

    坑 5：Dockerfile 拼写错误（silm）¶

    报错：docker build 时拉镜像失败（找不到 python:3.12-silm）
场景：FROM python:3.12-silm 写错，应该是 slim。
原理：镜像版本名不存在，构建器去仓库找不到就报错。
解决：改成 FROM python:3.12-slim。
预防：名字拼错程序找不到 —— 这类报错容易被误判为网络/权限问题，
      先核对拼写再怀疑网络。

    坑 6：docker build 忘了最后的点¶

    报错：docker: 'docker build' requires 1 argument
场景：docker build -t ypproject:v1 少了最后的 .。
原理：. = 构建上下文 —— 告诉 Docker 从哪个目录找 Dockerfile 和文件。
解决：补上：docker build -t ypproject:v1 .
预防：docker build 结尾必须给 PATH（哪怕就一个点）。

    坑 7：compose.ymal 文件名拼错¶

    报错：no configuration file provided: not found
场景：文件保存成了 compose.ymal（y-m-a-l），应该是 compose.yaml。
原理：Docker 只认标准文件名：compose.yaml / compose.yml（官方首选），
      为向后兼容还支持 docker-compose.yaml / docker-compose.yml。
解决：mv compose.ymal compose.yaml（mv = 移动/重命名）。
预防：文件名拼错，程序找不到配置文件 —— 和坑 5 同族（名字错）。

    坑 8：YAML 冒号后没有空格¶

    报错：yaml: line 4: mapping values are not allowed in this context
场景：compose.yaml 里写了 images:nginx（冒号后没空格 + 多了 s）。
原理：YAML 的硬规则：key: value 冒号后必须有空格；且键名拼错（image 不是 images）。
解决：改成 image: nginx；用 cat -A 查看文件真实内容（显示隐藏字符）。
预防：YAML 对格式极其敏感 —— 冒号后空格、缩进对齐，错一个就炸。

    坑 9：compose up 复用了失败残留的容器¶

    现象：docker compose ps 里 web1 的 PORTS 列是空的，curl 8080 连不上。
场景：第一次 up 时 8080 被占（web1 创建失败留残），第二次 up 直接复用。
原理：docker compose up 是增量的 —— 容器已存在就只 start 不重建；
      失败留下的残缺容器会被继续用（端口映射缺失被保留）。
解决：docker compose down 清场 + up 全新重建。
预防：遇到诡异状态，先 down 再 up，别在残局上折腾。

    坑 10：nginx 镜像里没有 wget¶

    报错：sh: 1: wget: not found
场景：想用 wget 验证容器互访，nginx 精简镜像里没这工具。
原理：精简镜像只带自己需要的工具。
解决：用 busybox 镜像当"探针"（自带 wget/ping，只有几 MB）。
预防：容器里用工具前先确认镜像里有没有；busybox 是万能探针。

    坑 11：rmi 删不掉镜像（容器占用）¶

    报错：conflict: unable to delete localhost:5000/ypproject:v1
      (must be forced) - container xxx is using its referenced image
场景：docker rmi 删镜像，被之前 docker run 留下的 Exited 容器拦住。
原理：只要容器存在（哪怕已退出），它引用的镜像就删不掉 ——
      镜像保护机制（和 Volume in use 同款）。
解决：docker rm <容器> 删掉容器 → 再 docker rmi <镜像>。
预防：删镜像前先 docker ps -a 看有没有容器在用。

    坑 12：pull 回来的镜像名带地址（短名 run 失败）¶

    报错：docker run ypproject:v1 → Unable to find image 'ypproject:v1' locally
      → pull access denied for ypproject, repository does not exist
场景：从 localhost:5000 拉回镜像后，用短名 run。
原理：镜像名 = 地址 + 名字 + 版本；pull 回来的名字是
      localhost:5000/ypproject:v1（带出身地址）。Docker 按名字精确匹配，
      短名不存在 → 自动去 Docker Hub 找（也不存在）→ 报错。
解决：docker run localhost:5000/ypproject:v1（用全名）。
预防：记住"不带地址 = 默认 Docker Hub"；run 用 pull 回来的全名。

    坑 13：tag 参数方向写反¶

    报错：Error response from daemon: No such image: ypproject:v1
场景：想给镜像加短名，写了 docker tag ypproject:v1 localhost:5000/ypproject:v1。
原理：docker tag <已存在的源> <新名字> —— 写反了方向，源（短名）不存在。
      而且 tag 是"加别名"不是"重命名"：源镜像保留，只是多一个名字。
解决：docker tag localhost:5000/ypproject:v1 ypproject:v1（源是长名）。
预防：参数顺序 = 先有的，后想要的名字。

    坑 14：wget 的 -o 和 -O 大小写¶

    现象：wget -q -o- http://web1 没有任何输出。
原理：wget 里大写 -O = 输出到终端（stdout）；小写 -o = 输出到文件。
      -o- 把内容写进了名为 "-" 的文件，终端自然没显示。
解决：用大写：wget -q -O- http://web1。
预防：命令参数大小写敏感 —— 不确定时查 wget --help。

    坑 15：Volume 删不掉（卷被容器占用）¶

    报错：Error response from daemon: remove ypdata: volume is in use
场景：docker volume rm ypdata 被容器 B 拦住（当时已 Exited）。
原理：卷被容器"引用"时删不掉 —— Docker 检查的是容器是否存在
      （包括 Exited），不只是是否运行。和坑 11 的镜像保护同款机制。
解决：docker rm <容器> 删掉引用容器的容器 → 再 docker volume rm。
预防：删卷前先确认没有容器挂载它。

    今日总结¶

    今天把 Docker 主干完整走完：生命周期 → 数据 → 端口 → 网络 → Dockerfile → Compose → Registry → 云服务器 → 科研工作流。

    • 最值钱的是方法论：遇错先看报错原文（Docker 的报错其实都写得很清楚），再拆解、再修 —— 今天 15 个坑都是这么过来的
    • 最值钱的是心智模型：容器=一次性房间、镜像=模具、-p=开窗、--network=专线、tag=贴名片、Registry=仓库
